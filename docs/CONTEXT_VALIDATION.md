## 长材料验收的具体行为

该验收使用受控采集工具，正文为长中文材料，末尾加入每次随机生成的 proof 标识。
模型事先不知道该标识。客户端主动设置 14000 tokens 软上限以触发压缩，服务实际容量
仍为 262144。结果：

- 采集工具只执行一次，模型使用 `artifact_search` 找回正文末尾的标识并准确报告。
- 共 4 次真实模型请求，浏览器未启动。
- 压缩前估计 59441 tokens，目标 10594，压缩后 5682。
  这是估计的模型视图大小，不是原生 tokenizer 的精确计数。
- 压缩记录实际提交；保存的原视图和新视图均可按哈希校验。
- 重新创建资料存储实例后，读取的完整结果与原采集对象一致。
- 外部 MCP 能按任务 ID 检索和回读原文；`../outside` 被拒绝。

没有测试 262K 满窗口推理的速度、质量或长距离语义理解；容量识别与可恢复裁剪不能
代替这些测试。该测试材料也不代表真实站点业务采集结果。

## 保留的失败及修复

`logs/live-harness/harness-30000-20260928-v070-final/receipt.json` 保留一次 **8/9** 回归。
当时采集和加工已经完成，但模型把 `history_read` 写成顶层 action，连续触发
`Unknown browser action`，最终答复阶段失败；首步另有一次不合法 JSON。

修复只兼容宿主已公开注册工具的动作简写，仍通过注册表和参数 Schema 校验。
新增测试确认未公开工具不被接受、错误参数仍失败。没有对不合法 JSON 放宽成任意执行。
随后 `...-v070-repaired` 和上述最终 `...-v070-release` 均为 9/9。
保留失败结果，而不将生成了文件等同于整个任务已完成。

另加测试覆盖服务暂时离线后自动模型发现恢复、服务更换模型时容量刷新、
显式模型不误用其他模型容量，以及处理中模型改变时拒绝混入已冻结的方法。
