# 通用文档能力诊断与实测

日期：2026-09-30。任务是从已知官方地址下载中国、美国、日本各一部专利法，输出每部
法律一个 JSON 对象、articles 数组中每条一个元素。这是通用文档处理的验收样例，
不是内置业务能力，也不是自主检索来源的测试。

结论：工具能力与执行流程均有已复现的缺陷，本次修复针对通用层。三国任务尚未全部
自主完成。最终本地组件回归 183 项通过；最近一次真实运行中国通过，美国仍有合并编号
未拆开，日本未导出。最后的参数诊断与展开大小限制只做了组件回归和旧候选回放，
没有再启动一轮完整三国任务，不能据此宣称剩余任务已被解决。

本页前述实测和 183 项回归对应提交 `4a9e26d`。后续在同日补了两处恢复代码缺陷，
187 项回归通过，见下面的补充记录；原真实执行回执和机器报告的源码指纹保持原有版本。

## 先纠正验收口径

此前 `46d56a3` 使用专门的国家解析器完成了 82 / 176 / 464 条的复制与校验。它能证明
配置好的适配器工作，但不能证明智能体能自主处理新文档。该适配器、专用 Skill、配置
和加工 profile 已删除；旧交付和验收记录保留，并标为历史适配器结果。

运行层没有这三个国家的网址、选择器、条号表达式或预期条数。测试驱动只向智能体提供
目标、官方 URL 和输出要求。特定样例的断言位于 `scripts/live_patent_laws_eval.py` 的
oracle 中，仅在智能体停止后读取实际输出，不能向规划器提供处理方法或修正答案。

## 根因按层分开

| 层次 | 实测问题 | 通用修复与边界 |
|---|---|---|
| 网络工具 | 原始 web_fetch 拒绝服务器主动发送的 gzip；浏览器回退可访问 | 限量解压 gzip/deflate，保存响应字节；这是工具缺陷 |
| 加工能力 | 原加工层依赖事先注册的 llm/mapping 方法，缺少现场研究文档结构及完整加工的原语 | 新增检查、解码、声明式分组、预览、复核、导出；不执行模型生成的任意代码 |
| 工作流 | 能写出 JSON、结构树能还原，就被当成按用户要求拆分完成 | 分开规则验证、来源守恒、模型语义复核和实际文件验收；它们提供不同强度的证据 |
| 上下文 | 近期动作只显示 action=tool，丢了工具名和参数；成功调用默认建议 retry | 保留有界原始调用及可恢复引用，成功后检查结果；重复动作反馈具体证据 ID |
| 工具结果记忆 | 结果只取前 500 字符，来源 URL、哈希等元数据占满前缀，实际样本从近期记忆消失 | 有界结构化投影保留观察字段与原始历史引用；旧检查点从原始记录恢复。该缺陷已复现，但未证明它是重复调用的唯一原因 |
| 复核上下文 | 样本省略 annotations，文本被截短，复核却据此认定输出字段/正文缺失；凭记忆猜总数 | 传递实际字段、显示截断、范围统计、未选中同类节点；拒绝意见核对证据引用 |
| 候选状态 | 读取 document_review 后，结构预览覆盖了先前拒绝结论，规划器又尝试导出 | 审查状态持续绑定 job_id；后续读取、导出不能清除拒绝结论，直到修订候选通过复核 |
| 负面反馈 | 复核已有可核验的问题引用，却因另一项清单错误被整体丢弃，主模型只看到“无结论” | 先核验具体问题；拒绝可返回已核验的引用，不把未经核验的清单一并传递。接受仍要求完整检查 |
| 检查点恢复 | 审查程序已更新，旧检查点仍声称“无结论”，主模型恢复后立即重复报告未完成 | 用审查规则/配置/输出契约指纹标记过期结论，恢复原任务已保存的候选规则并要求重审；宿主不代写新规则 |
| 规则参数 | 编号提取已经截掉后续标号，拆分分隔符却仍照常运行；复核漏看例外记录 | 诊断分隔符落在捕获范围之外的情况，优先展示相关记录；不自动补写编号 |
| 输出资源 | 一个来源片段对应大量组合标号时，正文随记录数成倍复制 | 在生成记录前核对实际展开文本预算；拒绝过量展开并保留来源 |
| 模型决策 | 主模型可能把结构标题当记录，放宽自己提出的约束；同一模型复核也可能漏判 | 仍须独立验收。引用存在、格式正确、模型同意，均不构成语义正确的证明 |

这说明“差工具”和“流程没设置好”同时存在。加入更多网站专用工具会掩盖问题；只有
工具、状态记忆、证据投影、失败恢复和验收一起工作，才可能可靠处理新的来源。

## 实测配置与证据

- 30000 服务实查为 Qwen3.8-27B-Q5_K_M，上下文 262,144 tokens。
- 使用 `examples/documents-30000.json`，未开启额外 MCP、专用 Skill 或预设加工方法。
- 学习关闭，防止把未验收的方法自动纳入经验；每次测试使用新目录和源代码快照。
- 独立复核使用同一模型的单独上下文，不能称为跨模型审计。
- 试验中开启推理曾出现重复推理、输出耗尽；当前使用非推理模式。
- 本地回归：183 项通过，84.41 秒；`pip check`、Skill 校验通过。打包结果记录在机器验收文件。
- 非法律测试覆盖设备手册、目录条目、注释、嵌套 XML、重复标号、附表、解码来源链、
  正则超时、篡改检测和完整记录按 job_id 交给加工子会话。这些是组件测试，不是泛化证明。

`20260930-generic-reviewed` 是一轮冻结代码的实测：62 次模型调用，达到 1,200 秒上限；
中国输出 82 条通过独立原文检查，美国、日本未导出。失败轨迹揭示了复核视图缺失信息
导致错误返工的问题。它不是三国成功结果。

`20260930-generic-evidence` 是另一轮冻结代码的实测：34 次模型调用，规划器和文件门槛
均报告完成，但独立验收失败。中国把章标题混入条文数组，变成 98 条；美国输出 168 条，
遗漏独立的废止/改号记录且将注释并入正文；日本输出 464 条，旧断言通过，但记录本身未
显式携带部分 ArticleCaption（原文 fragments 仍完整）。这些结果证明“同一模型分上下文
复核”仍能误通过，文件哈希正确不能替代任务语义验收。

后续通用修复要求复核明确记录单位、逐个检查样本，给缺陷分类并核验引用位置；同时
补充每条记录的源节点数量、正文类别及实际归属。对上轮真实候选重放，已分别拒绝中国
错误记录单位、美国正文/注释混合，以及日本记录内缺少标题说明的问题。独立测试也增加
了正文与其所属条文的对应关系及标题说明检查。重放拒绝错误候选不等于自主完成新任务。

`20260930-generic-typed-review` 在恢复检查点的第二次尝试中又进行了 33 次模型调用，
规划器报告完成，但独立验收仍不通过：中国 82 条仍混入章标题，美国 168 条仍少了独立的
废止/改号记录，日本 464 个源节点通过当时的原文、标题说明及附表保留检查。测试驱动随后
增加更严格的文字要求：废止、改号和同标题多条号也必须各自成为数组元素。这是本次
测试追加的明确约束，并非用户曾逐项指定这些细则，也不是提供提取规则。新复核要求
逐项判断未作为记录起点的材料是否属于请求单位，不能仅凭注释中
保留原文就接受。

`20260930-generic-coverage/attempt-3` 沿用同一任务检查点，42 次调用后达到 1,200 秒上限。
中国 82 条通过全部独立断言；美国未导出，日本已解码并形成候选，但未导出。该次尝试
运行期间源码未改变。此前两次尝试因复现通用接口说明及候选状态缺陷而人工停止，均有
中断审计与源码快照。因此这一系列是开发诊断迭代，不能包装为一次无人干预的成功运行。

这轮轨迹还显示，主模型在已拿到完整拒绝意见、引用证据和通用字段说明后，仍重复提交
相同规则；也曾多次读取完整历史后继续重复读取。信息保留的缺陷确实存在，模型决策本身
也仍有局限。修复已覆盖的机制不能推导为“模型一定能自主完成任意任务”。

`20260930-generic-observation` 初次运行进行了 40 次模型调用，中国 82 条通过独立断言。
美国、日本未导出，主模型如实报告 incomplete。这次在冻结代码下复现了负面反馈丢失：
美国复核指出两处正文节点类别未覆盖，日本复核指出三处标题说明未保留在记录内，但
两份拒绝答复都因其他清单项填写错误而成为 review_inconclusive。对原始答复进行确定性
重放后，新验证器保留了这些有原文引用的问题，同时丢弃未经核验的清单。记录在该运行的
`negative-review-replay.json`；这只能证明反馈处理修正，不能代替完整任务验收。

第二次尝试只有一次模型调用，直接沿用旧检查点的阻塞结论返回 incomplete，没有新增
导出。该结果进一步暴露了审查版本与任务状态未衔接的问题。补上指纹检查后，第三次
尝试从原检查点恢复，并只提供这个任务自己已生成、已保存的候选规则用于重新预览。

第三次尝试进行了 20 次模型调用后超时，该次运行期间源码未变。中国 82 条再次通过全部
断言；美国导出 175 个对象，全部 175 个标题和 1,161 个正文段落的相关断言通过，正文与
注释分离、正文归属也通过，但共用标题的两个编号仍被合成一条，未达到 176 个独立对象。
主模型设置的 key_pattern 只捕获首个编号，key_separator 无法拆分已被截掉的部分；
复核也误接受了该候选。日本取得解码来源并多次修改候选，但未导出。因此该系列
40 + 1 + 20 次调用是带开发干预的恢复尝试，不能称为冻结版本的一次自主成功。

最终只读复查还发现旧日本断言的范围不足：464 个 Article 节点中，两个节点分别合并
表示 55–63 和 129–130。若要求每个编号独立，应展开为 473 个对象。早期日本输出保留了
这 464 个节点的正文、标题说明、附则与附表，但没有展开这两个合并标号，不能再称为
“每个条号均独立通过”。运行后的 oracle 已增加合并范围检查；旧验收文件保持原样，
新复查另存，避免覆盖当时记录。该范围解析只用于测试验收，不进入智能体运行层。

最后的通用编号诊断在美国原候选上定位到第 62 个对象：捕获结果只有 155，未消费的后缀
以分隔符开始，仍含 155A。新投影优先展示该对象；记录的唯一身份 id 与允许重复的
显示标号 key 也明确区分。三份选定历史输出均能被当前引擎原样重放，文件未修改。
这是诊断信息与组件行为的验证，没有再次调用模型，也没有宿主手工修订国家提取规则。

仍未解决的部分包括主模型在有效反馈后的重复动作、抽样复核的语义误判，以及通用规则
对复杂组合标号/区间重构的覆盖范围。较大上下文窗口并没有自动消除这些问题。本次
结果不支持总体成功率、单项修复的因果效果或跨网站泛化结论。

详细结果在 `docs/validation/generic-documents-20260930.json`。
完整运行材料位于本机 `logs/live-generic-documents/` 与 `deliveries/generic-documents/`，
失败目录不会覆盖或删除。

## 正确的处理流程

1. 把用户要求转成记录单位、字段、原文保留和来源版本要求。
2. 获取完整材料，记录 URL、时间、内容哈希；网络失败再判断浏览器交互是否必要。
3. 检查真实格式、标题、正文、注释、重复结构和未选中内容，再提出声明式处理规则。
4. 用完整材料试跑，检查首中尾、例外条目和未处理区域。修改规则应解决证据中的问题，
   不能为了通过检查而扩大或取消原有约束。
5. 原文复制、分组、去重和导出由确定性工具执行；需要语义加工时按来源/任务 ID 交给
   子智能体，并保留可追溯记录。不要在父子智能体间反复抄写长文。
6. 复核具体证据，再核验实际文件；模型接受只作为意见。没有证据支持的完成状态应
   报告为未完成或部分完成，并保留可恢复状态。
7. 只有经独立回放验证有改善的方法，才进入后续任务可用的经验。

PDF/OCR、动态 DOM 导入以及自动生成任意加工程序，不在本次新增能力范围内。
美国样例是 GovInfo 的 2024 Title 35 版本；本测试不宣称它是 2026 最新法律。

## 后续恢复修复与下一步

两处新增缺陷先以失败用例复现，然后修正：

- 重复动作签名原本包含整个 action，reason 改写能使相同工具、参数、结果变成不同签名。
  现在只按实际执行的工具名和参数识别操作，仍保留页面/结果变化作为新进展。
- 结构化近期历史或压缩历史主动返回空列表时，规划器用 `or` 回退到旧历史，覆盖投影
  的选择。现在空列表保持为空，只有没有投影时才兼容旧格式。

本地全量回归 187 项通过，85.89 秒。新增用例同时验证改参数/改证据仍计为新变化，
以及旧格式调用者仍能使用回退。这次没有新增真实模型调用，未重写任何法律输出。
上一轮的 46 个工具动作没有 reason；只读审计也没有发现该轮两组历史里的动作 ID
重叠。因此这两处是已复现的代码健壮性缺口，不能声称它们就是上轮超时的直接原因。

剩余问题应按执行恢复、通用标号操作、异常复核、上下文聚焦的顺序推进。上轮第 48 步
真实规划输入为 117,572 tokens，近期历史 192,739 字符、扩展状态 42,830 字符、任务记忆
33,557 字符。这说明需要检查每步输入与耗时，而非仅检查是否超出模型窗口；这些统计
不能单独证明某种上下文策略能提高任务成功率。后续完整任务验收仍待进行。
